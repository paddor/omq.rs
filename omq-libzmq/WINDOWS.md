# Windows support

`omq-libzmq` supports Windows through the MSVC Rust target. Pull request CI
builds, lints, and tests `x86_64-pc-windows-msvc`. MinGW targets are not part
of the tested support matrix.

The general C API surface and its compatibility gaps are documented in
[doc/compatibility.md](doc/compatibility.md). This file covers only Windows
differences.

## Supported functionality

- All socket types listed in the compatibility document
- `inproc://` for process-local communication
- `tcp://`
- `ipc://name` through Windows named pipes
- `ws://` and `wss://`
- NULL, PLAIN with ZAP or a fixed allowlist, and CURVE
- LZ4 and Zstd transport compression
- Blocking, nonblocking, and timeout-based send/receive
- `zmq_poll()` and the poller API for OMQ sockets

## IPC endpoints

On Windows, `ipc://name` maps to `\\.\pipe\name`. For example:

```c
zmq_bind(server, "ipc://my-service");
zmq_connect(client, "ipc://my-service");
```

The name must contain 1 to 256 UTF-8 bytes, must not contain control characters
or `< > : " | ? *`, and must not be a reserved Windows device name. Unix
filesystem paths and Linux abstract endpoints do not apply on Windows. Use
`inproc://` instead when both sockets belong to one process.

## Polling

OMQ sockets use manual-reset Windows events internally. Poll sets may contain
more than the 64 handles accepted by `WaitForMultipleObjects()`: the first
batch participates in the blocking wait, then all batches are scanned. Use a
finite timeout when readiness in later batches must be noticed promptly.

Windows does not expose the internal event as a libzmq file descriptor:

- `zmq_getsockopt(socket, ZMQ_FD, ...)` returns `ENOPROTOOPT`.
- Raw file-descriptor entries, where `zmq_pollitem_t.socket` is null, are not
  monitored on Windows.
- `zmq_ppoll()` works only with a null signal mask, on every platform.

Use `zmq_poll()` or the poller API instead of `ZMQ_FD`.

## Building

Install Rust 1.93 or newer and the Visual Studio C++ build tools, then build
from a Developer PowerShell:

```powershell
cargo build -p omq-libzmq --release --target x86_64-pc-windows-msvc
```

The DLL is written to:

```text
target\x86_64-pc-windows-msvc\release\omq_zmq.dll
```

The same directory contains the MSVC import and static libraries generated by
Rust. Dynamic linking is recommended. Include `omq-libzmq\include\zmq.h`, link
the DLL import library, and put `omq_zmq.dll` beside the executable or on
`PATH`. Do not define `ZMQ_STATIC` when consuming the DLL.

For static linking, define `ZMQ_STATIC` before including `zmq.h` and link the
Rust static library plus its Windows system-library dependencies.

## Building the C security examples

After the release build, compile the PLAIN and CURVE examples with MSVC:

```powershell
cl /nologo /std:c11 /W4 /I omq-libzmq\include `
  omq-libzmq\examples\plain.c `
  /link /LIBPATH:target\x86_64-pc-windows-msvc\release omq_zmq.dll.lib

cl /nologo /std:c11 /W4 /I omq-libzmq\include `
  omq-libzmq\examples\curve.c `
  /link /LIBPATH:target\x86_64-pc-windows-msvc\release omq_zmq.dll.lib

Copy-Item target\x86_64-pc-windows-msvc\release\omq_zmq.dll .
.\plain.exe
.\curve.exe
```

## Testing

On Windows:

```powershell
cargo test -p omq-libzmq --target x86_64-pc-windows-msvc
cargo clippy -p omq-libzmq --all-targets --all-features `
  --target x86_64-pc-windows-msvc
```

Repository CI also exercises Windows-specific named-pipe and large poll-set
tests. Use [DEVELOPMENT.md](../DEVELOPMENT.md) for the full test matrix.
